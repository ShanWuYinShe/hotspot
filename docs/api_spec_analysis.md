# HotSpot API 规范问题分析报告

> 从产品经理和架构师角度对 API 规范文档的详细分析

## 执行摘要

本报告识别了 API 规范中的**类型定义不一致**、**错误码设计缺陷**、**文档结构问题**和**设计缺陷**等四大类问题，共**23个具体问题**，其中**严重问题8个**，**中等问题10个**，**轻微问题5个**。

## 一、类型定义冗余与不一致问题（严重）

### 1.1 文件重复：`api_spec_base.mdc` 与 `api_spec_common_types.mdc` 内容几乎完全相同

**问题描述**：
- `api_spec_base.mdc` 和 `api_spec_common_types.mdc` 两个文件内容高度重复（约1200行）
- 在 `api_spec.mdc` 索引中，`api_spec_common_types.mdc` 被描述为"API 设计原则、通用类型定义、命名规范、分页语义、安全性实践等"
- 但实际读取发现两个文件内容几乎完全相同

**影响**：
- 维护成本高：修改一处需要同步修改另一处
- 容易产生不一致：两个文件可能在不同时间被修改，导致内容分叉
- 开发者困惑：不清楚应该参考哪个文件

**建议**：
- **方案1（推荐）**：删除其中一个文件，统一使用 `api_spec_base.mdc`，更新索引文档引用
- **方案2**：如果确实需要分离，明确两个文件的职责边界：
  - `api_spec_base.mdc`：基础类型定义（Domain Primitives & Entities）
  - `api_spec_common_types.mdc`：设计原则、约定、最佳实践（不包含类型定义）

**严重程度**：🔴 严重

### 1.2 类型命名不一致：`UserCard` vs `UserDetailItem` vs `UserProfile`

**问题描述**：
- `api_spec_base.mdc` 使用：`UserDetailItem`、`UserRelationshipData`、`GroupMyStateData`
- `api_spec_common_types.mdc` 使用：`UserCard`、`Relationship`、`Membership`
- 规则文件（`.cursor/rules/api_spec_user.mdc`）使用：`UserProfile`、`AdminUserProfile`
- 实际代码实现使用：`UserItem`、`UserDetailData`、`MyProfileData`

**影响**：
- 前后端对接困难：类型名称不统一导致理解偏差
- 文档与实现不一致：规范文档中的类型名称与实际代码不匹配
- 客户端开发困惑：不清楚应该使用哪个类型名称

**建议**：
1. **统一命名规范**：确定一套权威的命名规则并严格执行
   - 建议采用 `api_spec_base.mdc` 中的命名（`UserCard`、`Relationship`、`Membership`）
   - 或采用代码实现中的命名（`UserItem`、`UserDetailData`）
2. **建立类型映射表**：在规范文档中明确说明规范类型与实现类型的对应关系
3. **更新所有引用**：统一更新规则文件、代码注释、API 文档中的类型名称

**严重程度**：🔴 严重

## 二、错误码设计问题（严重）

### 2.1 错误码 `10300` 的使用规则过于复杂且容易混淆

**问题描述**：
- `10300` 被定义为"资源不存在（泛化，向后兼容）"
- 文档说明："新增 API 必须使用细分码（10310-10389），禁止使用 `10300`"
- 但同时又说："现有 API 可继续使用 `10300`，建议逐步迁移到细分码"
- 客户端处理建议："默认按 `10300` 统一兜底；仅在明确需要差异化体验时再针对细分码做特殊分支"

**问题**：
- 规则矛盾：既要求新增 API 禁止使用 `10300`，又建议客户端统一按 `10300` 处理
- 迁移路径不清晰：现有 API 何时迁移、如何迁移没有明确计划
- 客户端实现困难：需要同时处理 `10300` 和细分码，增加复杂度

**建议**：
- **方案1（推荐）**：完全废弃 `10300`，所有 API 必须使用细分码
  - 更新现有 API 文档，明确每个接口使用的细分码
  - 客户端统一按细分码处理，不再保留 `10300` 的兜底逻辑
- **方案2**：保留 `10300` 作为真正的"未知资源类型"错误码
  - 明确 `10300` 仅用于无法确定资源类型的场景（如通用资源查询接口）
  - 所有具体资源类型必须使用细分码

**严重程度**：🔴 严重

---

### 2.2 错误码范围划分不够清晰

**问题描述**：
- `10200-10299`：权限与访问控制
- `10300-10399`：资源不存在 / 不可访问
- 但 `10200`（权限不足）和 `103xx`（资源不存在）的边界不清晰

**具体问题**：
- 文档说明：`/public/**` 下资源不存在/不可见时统一返回 `103xx`（不泄露存在性）
- 文档说明：`/protected/**` 下资源不存在返回 `103xx`，资源存在但不可访问返回 `10200`
- 但实际场景中，隐私限制导致的"不可见"应该返回哪个错误码？

**建议**：
- 明确错误码语义：
  - `10200`：资源存在，但当前用户无权限访问（需要登录/提升权限）
  - `103xx`：资源不存在或对当前用户不可见（不泄露存在性）
- 在错误码文档中补充典型场景的错误码选择决策树

**严重程度**：🟡 中等

---

### 2.3 错误码 `10204` 和 `10205` 的命名不够直观

**问题描述**：
- `10204`：非管理员（NOT_ADMIN）
- `10205`：管理员权限不足（ADMIN_PERMISSION_DENIED）
- 两者都属于权限错误，但错误码不连续（中间跳过了 `10202`、`10203`）

**建议**：
- 重新分配错误码，使管理员相关错误码连续：
  - `10204`：非管理员
  - `10205`：管理员权限不足
  - 或合并为一个错误码 `10204`，通过 `message` 字段区分具体原因
- 在错误码文档中补充错误码分配规则，避免随意跳号

**严重程度**：🟢 轻微

---

### 2.4 错误码 `10420` 的语义不够清晰

**问题描述**：
- `10420`：不是好友关系（好友 = 双方互相关注，需要成为好友才能执行此操作）
- 这个错误码属于"业务冲突"类别，但语义更像是"权限不足"

**建议**：
- 考虑将 `10420` 移到 `10200-10299` 范围，或创建新的错误码 `10214`（需要好友关系）
- 明确区分：
  - `10214`：需要好友关系才能执行此操作
  - `10420`：当前操作与好友关系状态冲突（如：尝试取消关注一个不是好友的用户）

**严重程度**：🟢 轻微

## 三、分页、隐私等基础机制问题（中等）

### 3.1 分页机制设计完善，但缺少边界情况说明

**问题描述**：
- 文档详细说明了 cursor-based pagination 的使用流程
- 但缺少以下边界情况的说明：
  - `limit=0` 或 `limit>100` 的处理方式
  - `cursor` 为空字符串的处理方式
  - 同一 `cursor` 多次请求的幂等性保证
  - 服务端数据变更对 `cursor` 稳定性的影响

**建议**：
- 补充边界情况处理说明：
  - `limit` 超出范围时返回 `10003`（参数值超出范围）
  - `cursor` 为空字符串时视为首次请求
  - 同一 `cursor` 多次请求应返回相同结果（幂等性）
  - 数据变更对 cursor 的影响：新增数据不影响已返回的 cursor，删除数据可能导致 cursor 失效

**严重程度**：🟡 中等

### 3.3 隐私字段响应格式与类型定义不一致

**问题描述**：
- 文档要求：隐私限制时字段不存在（`undefined`）
- 但类型定义中使用 `?:` 表示可选，这在 TypeScript 中既可以是 `undefined` 也可以是字段不存在
- 缺少明确的序列化规范：服务端如何确保字段不存在而不是 `undefined`

**建议**：
- 明确序列化规范：
  - 使用 `skip_serializing_if` 确保字段不存在时完全不序列化
  - 禁止使用 `null` 表示隐私限制
- 在类型定义中补充注释：`// 隐私限制时字段不存在（undefined），不使用 null，不序列化`

**严重程度**：🟡 中等

## 四、设计缺陷（严重）

### 4.1 缺少 API 版本管理策略

- 所有 API 使用 `/api/v1/` 前缀，但缺少版本管理策略

  - 何时需要创建新版本（v2）？
